## Fiabilité des décisions SARIF

Le moteur échoue si le scanner échoue, si le fichier SARIF manque, ou si la
structure requise du rapport est invalide. Les résultats `pass`,
`review`, `open`, `informational` et les niveaux `note`/`none`
ne sont pas comptés comme failles actives. Les suppressions explicitement
acceptées ne sont pas comptées, mais elles restent traçables ; les suppressions
rejetées/en cours de revue restent actives.

Le mode strict bloque les **signalements actifs détectés**, pas des vulnérabilités
confirmées. Les règles externes et bases CVE peuvent contenir des faux positifs
ou être incomplètes. La correction d'une alerte doit dépendre d'une vérification
du contexte, de l'atteignabilité et de l'impact ; pas de son nombre seul.

## Limites importantes et suites

- Semgrep utilise `p/security-audit` ; ce jeu de règles n'est pas exhaustif.
- Trivy se limite aux analyses de dépendances et configurations prises en charge,
  aux niveaux HIGH/CRITICAL ; une CVE signalée n'est pas forcément atteignable.
- Gitleaks couvre l'historique Git accessible ; absence de signalement ne prouve
  pas l'absence de secret dans un système externe.
- zizmor s'exécute hors ligne avec seuil MEDIUM : certains contrôles nécessitant
  l'API GitHub sont hors périmètre.
- Un jscpd exact détecte une copie littérale ; il peut ignorer les clones
  reformattés. Une copie volontaire n'implique pas forcément du travail à faire.
- La couverture de tests applicatifs n'est pas automatiquement mesurée si aucun
  rapport adapté n'est produit.
- Les protections de la branche principale doivent être administrées
  séparément, avec des contrôles obligatoires.

**État de ce rapport :** résultats réels vérifiés sur la PR, sans revendication
de sécurité totale. Révision humaine recommandée avant fusion ou release.
